# [M8-3] Backfill Riwayat Log Sinkronisasi di Latar Belakang

**Milestone:** M8 — Fase 3  
**Estimasi Ukuran:** M  
**Area:** `mobile`  

---

## Task Brief

- **Task ID / Judul:** `M8-3` — Backfill Riwayat Log Sinkronisasi di Latar Belakang
- **Tujuan:** Mengimplementasikan mekanisme penarikan riwayat review logs masa lalu secara malas (lazy backfill) di latar belakang pada perangkat baru untuk visualisasi riwayat jangka panjang.
- **Bagian Dokumen Acuan:** §7.4 (Perangkat baru bootstrap & backfill lazy), §15 (M8 Fase 3)
- **Input:** Endpoint `GET /v1/sync/pull` dengan entitas `logs` dari backend.
- **Output:** Service `LogHistoryBackfillService` di `apps/mobile/lib/data/sync/`.

### Langkah Implementasi
1. Pada perangkat baru (bootstrap), klien awalnya hanya menarik `cards, settings, progress` (tanpa log) untuk mempercepat onboarding (§7.4).
2. Implementasikan service latar belakang untuk menarik riwayat `review_logs` terdahulu secara bertahap (chunking berbatas) saat perangkat terhubung Wi-Fi dan idle (§7.4, §15).
3. Simpan log review historis yang ditarik ke dalam tabel lokal `review_logs` menggunakan aturan merge union (§7.3).
4. Pastikan proses backfill tidak mengganggu prioritas antrean sync outbox atau transaksi review aktif pengguna.

### Tes yang Harus Ada
- [ ] Integration test: bootstrap awal tidak menarik tabel log, lalu service backfill menarik log secara bertahap.
- [ ] Unit test: penulisan log historis tidak menduplikasi ID yang sudah ada (idempoten).

### Observability yang Harus Ada
- [ ] Log DEBUG mencatat progres jumlah log historis yang berhasil di-backfill.

### Di Luar Cakupan (Out of Scope)
- Penghapusan log di server (log di server disimpan permanen/terpartisi).

### Aturan Teknis Ketat & Larangan (§0, §4.3, §10, §12, §16)
- ⚠️ Bootstrap perangkat baru wajib ringan; backfill log WAJIB lazy di latar belakang (§7.4).
- ⚠️ Penggabungan log wajib mematuhi aturan union tanpa menimpa (§7.3).
