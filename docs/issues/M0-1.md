# [M0-1] Monorepo, linter, formatter, CI kerangka

**Milestone:** M0 — Fondasi  
**Estimasi Ukuran:** M  
**Area:** `infra`  

---

## Task Brief

- **Task ID / Judul:** `M0-1` — Monorepo, linter, formatter, CI kerangka
- **Tujuan:** Menginisialisasi struktur monorepo sesuai standar §14.1 beserta tooling linting, formatting, dan kerangka pipeline CI GitHub Actions.
- **Bagian Dokumen Acuan:** §0 Aturan 3 & 4, §14.1 (Struktur monorepo), §14.3 (Pipeline CI/CD)
- **Input:** Dokumen teknis §14.1 dan §14.3
- **Output:** Struktur direktori monorepo di root repo, konfigurasi linter/formatter, dan workflow `.github/workflows/ci.yml`.

### Langkah Implementasi
1. Buat struktur folder monorepo persis sesuai §14.1: `apps/mobile/`, `apps/api/`, `packages/contracts/`, `content/` (`_pool`), `tools/content-cli/`, `infra/terraform/`, `docs/` (`runbooks/`, `adr/`), `.github/workflows/`.
2. Konfigurasi root tooling: pnpm workspace atau npm workspaces untuk TypeScript packages.
3. Setup ESLint dan Prettier dengan aturan strict untuk Node.js/TypeScript.
4. Setup `analysis_options.yaml` untuk Dart/Flutter dengan aturan linting ketat.
5. Konfigurasi Git hooks / lint-staged (jika relevan) dan validasi Conventional Commits.
6. Buat GitHub Actions workflow `.github/workflows/ci.yml` yang menjalankan linting dan formatting check untuk seluruh workspace pada setiap PR.

### Tes yang Harus Ada
- [ ] CI GitHub Actions berjalan dan berstatus hijau (green) pada PR kosong.
- [ ] Linter mendeteksi dan memblokir pelanggaran formatting / syntax error pada kode TypeScript dan Dart.

### Observability yang Harus Ada
- [ ] Log output GitHub Actions jelas dan rapi menampilkan langkah linting serta formatting.

### Di Luar Cakupan (Out of Scope)
- Implementasi kode fitur aplikasi mobile atau endpoint API bisnis.
- Penyusunan pipeline deployment produksi/staging.

### Aturan Teknis Ketat & Larangan (§0, §4.3, §10, §12, §16)
- ⚠️ Struktur monorepo wajib mengikuti §14.1 tanpa memindahkan atau mengubah nama folder inti.
- ⚠️ Trunk-based development dengan branch pendek dan conventional commits (§14.3).
- ⚠️ Dilarang menambahkan dependensi yang tidak relevan dengan fondasi linter/formatter.

### Definition of Done (DoD) (§0 Aturan 4)
- [ ] Seluruh kode implementasi tuntas sesuai spesifikasi di atas.
- [ ] Seluruh unit test & integration test yang disyaratkan lulus 100%.
- [ ] Linter dan formatter lulus tanpa error maupun warning.
- [ ] Log, metrik, dan tracing terpasang sesuai standar §10 tanpa kebocoran PII.
- [ ] Dokumentasi singkat atau `docs/decision-log.md` diperbarui jika ada keputusan teknis.
- [ ] Tidak ada `TODO` tersisa tanpa nomor issue aktif.
- [ ] Ukuran diff PR kurang dari ±400 baris diff (di luar file hasil generate kode).
